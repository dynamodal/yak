# Backup decisions

Decisions made while building backups and restore (`src/backup/`), for the owner's review.
The owner-facing description is in `docs/backups.md`.

| Decision | Why | How to change it |
| --- | --- | --- |
| A restore reads only the Yjs update (`update.ybin`) of each document; the readable files (JSON Lines, Markdown, JSON) are exports for people | The update is lossless and merges safely; rebuilding documents from readable files would be a second, hand-made import path with its own bugs | Add an importer for the readable files as a separate adapter later (it would create new records, not reproduce the CRDT state) |
| Each backup is a new folder named `<UTC time>_<device id prefix>` directly inside the picked folder; nothing is ever pruned (restore points are thinned since #65, see below; older full backups at the root never are) | Sorts by time; two devices backing up into one synced folder never collide; "keep all copies" | `backupName` and `BACKUP_NAME` in `format.ts`; pruning would be a new, explicit feature |
| `manifest.json` is written last, after every other file was read back and checked against its SHA-256 | A folder without a manifest is an interrupted backup and is never offered for restore; a write that the disk mangled fails at once instead of at restore time | `writeBackup` in `store.ts` |
| Time entries are partitioned by the UTC month of `start` (`partitionKey`), recorded as `{scheme: monthly, field: start, timezone: UTC}` in the manifest | Using the device's time zone would put the same entry in different files on different devices; the manifest lists files, so a later scheme still reads | `partitionKey` and `PARTITION` in `format.ts` |
| Document folders are the id with `/` replaced by `~` (`docs/space~work`) | Nested ids such as `space/work/notes/<id>` cannot clash with a document's own `notes/` folder; `~` never occurs in an id | `docFolder` in `format.ts` (the manifest records the folder, so old backups still read) |
| Automatic backups (timer stop, hourly) skip writing when the SHA-256 of all document updates equals the last backup in the same folder and that backup still exists; the check counts as "backed up" for the banner. "Back up now" always writes | An app left open all day would otherwise write identical copies every hour, forever | `exec` in `service.ts`; pass `force: true` everywhere to always write |
| Backup 5 seconds after the last `timer:stopped`; hourly while open; 15 seconds after start when the last backup is over an hour old | A stop–start–stop sequence makes one backup; opening the app after a break backs up soon | `STOP_DEBOUNCE_MS`, `HOURLY_MS`, `STARTUP_DELAY_MS` in `service.ts` |
| One run at a time: a promise chain in the tab (requests during a run merge into one follow-up run) and a Web Lock across tabs (automatic runs give up when another tab holds it) | Two tabs or a stop during an hourly run must not write overlapping backups; the follow-up catches changes made after the running backup took its snapshot | `run`/`begin` in `service.ts`, `webLock` in `runtime.ts` |
| Stale-backup banner: last backup (or unchanged check, or download) older than 24 hours, a failed last run, data but no backup ever, or folder permission/access lost. Threshold selectable 12 h, 24 h, 3 days, 7 days | The plan's 24-hour default; a fresh install with no data does not nag | `backupHealth` in `service.ts`, `STALE_CHOICES` in `BackupsView.tsx` |
| Where folders are not supported (Firefox, Safari): "Download backup" saves one JSON file (same manifest and checksums, text files as text, binaries as base64), restored from the same screen | One code path: the file unpacks into an in-memory folder and goes through the same verification and restore | `snapshotToBundle`/`bundleToDir` in `restore.ts` |
| Merge is the default restore. Replace is behind a confirmation checkbox, writes a safety backup first, keeps the replaced data on the device ("Merge it back"), deletes the document databases and reloads, then applies the backup | Yjs cannot un-delete inside a live document, so an exact replace needs fresh documents; the flag in localStorage makes an interrupted replace finish on the next start | `replace.ts` |
| After a replace, the shell's `initSpaceDoc` stamps `meta` before the backup is applied, so `meta.created_at` may differ from the backup and the state vector has one extra entry; all data maps are identical | Applying the backup before the shell opens documents would need a boot hook in `main.tsx` | Add a pre-boot hook to the shell and apply pending replaces there |
| On a paired device, replace changes only this device; peers send their data back when they connect | A replace that propagated would be a synced mass deletion, which needs its own design | Out of scope for the MVP |
| The backup service is started by the first backup component that renders (the banner, on every screen) | Modules get the store and bus only through the app context; no change to `main.tsx` | Start it from a module init hook if the shell gets one |
| `docDbName(id)` exported from `core/doc-store.ts` | Replace must delete exactly the databases the store uses; a test pins the two together | — |
| Deleted notes are not written as Markdown files; `notes.json` lists every note with `file: null` for deleted ones | A folder of deleted notes would mislead someone browsing the backup; the update keeps them | `exportDoc` in `snapshot.ts` |
| Note file names: unsafe characters become `_`, Windows reserved names get a `_` prefix, `.md` is added, and a case-insensitive clash gets the note id appended | Backups go to OneDrive and Windows folders; two notes may share a path after a sync | `notePath` and `safeSegment` in `format.ts` |
| Exports are sorted by UTF-16 code units, not `localeCompare` | The same data must always give the same files, whatever the browser's locale | `cmp` in `snapshot.ts` |
| History lists the newest 50 backups (reading 50 manifests) | Hourly backups add up; reading thousands of manifests on each visit would be slow | `listBackups(root, limit)` |
| Format version 1; a newer version is refused with "update the app"; `fixtures/backup-format-1.json` is a frozen version-1 backup that must keep restoring | There is no older format yet; the golden file is the "older format" test once version 2 exists | `FORMAT_VERSION` and `upgradeManifest` in `format.ts` |
| Incremental layout `<account>/{current,history,restore-points,manifest.json}` in the chosen folder; older full backups at the root stay and count as the oldest restore points | Backups stop growing by a full copy each run; nothing older is deleted (#65) | `src/backup/incremental.ts`, `exec` in `service.ts` |
| Segment files `<start>_<end>_<hash16>.seg`: a JSON header line plus the Yjs update; the hash is of the whole file; a run copies the names the folder lacks | Two runs or two devices never duplicate a file; thinned (merged) segments only add files, and overlapping segments apply harmlessly in Yjs | `encodeSegment`, `copySegments` |
| `current/` is a normal backup folder rewritten in place: only files whose checksum changed are written, files gone from the data are removed, `manifest.json` last | The readable mirror stays one folder and restores like any backup | `writeCurrent` |
| A restore point on every "Back up now" and when the newest is a week old; thinned to the newest per week for 4 weeks, per month for a year, then per year. The safety backup before a replace is not thinned in its run | Owner H2; thinning must never remove the backup being restored from | `thinRestorePoints`, `addRestorePoint(…, thin)` |
| Restore to a time = newest restore point (or older full backup) before it, plus every segment that began by it; each segment checked against the hash in its name; the result opens in the ordinary restore panel (counts, checksums, Merge or Replace) instead of the History tab | A fresh profile has no history log for the History tab to compare; the panel is the same preview every restore already has | `stateAtTime`, `TimeRestore` in `BackupsView.tsx` |
| The folder's account sub-folder name is the account id | One folder can hold several accounts; Restore to a time lists them | `findAccounts` |
| Encryption: one passphrase per account; PBKDF2-SHA256 (600,000 iterations) to a 256-bit key; AES-GCM with a fresh IV per file; file = `PDENC1` + IV + ciphertext. Salt, iterations and a check value (SHA-256 of key and a label) in the account document (`settings.backup_encryption`) and in plain `<account>/encryption.json` | The account document syncs the parameters to every device; the folder copy lets a fresh browser restore with only the folder and the passphrase (#66) | `src/backup/crypto.ts`, `encryption-state.ts` |
| Encrypted mode is per device (`StoredStatus.encrypted`); it encrypts every file the service writes (an `EncryptedDir` over the folder) and writes no readable exports (`createSnapshot({readable: false})`) | A shared computer or cloud folder (owner H6); names and counts must not leak | `exec` in `service.ts` |
| The key is a non-extractable `CryptoKey` in this device's IndexedDB; a device without it writes nothing and shows the error | No passphrase in storage; a wrong or missing key never produces an unreadable backup | `deviceKey` |
| Reading a file without the header returns it unchanged; reading an encrypted file with no key fails with "enter the passphrase" | Older plain backups share the folder; no silent garbage | `EncryptedDir` |
| Switching the mode rewrites `current/` once; files already in the folder (segments, older restore points) are left as they are; downloads are off while encryption is on | A plain download would defeat the mode; rewriting history files is a separate feature | `rewriteCurrent` in `service.ts` |

| (#219) The `?test` hooks and the 1000-iteration shortcut exist only in a test build (`YAK_TEST_BUILD=1`, set by `npm run e2e`); stored PBKDF2 `iterations` must be 100 000–10 000 000 (any positive count up to the cap in a test build), else `InvalidParamsError` | `?test` on the live site could weaken a new passphrase and sync that to every device; an unbounded count from the account document or `encryption.json` could freeze the tab or be weak | `MIN_ITERATIONS`/`MAX_ITERATIONS` in `src/backup/crypto.ts`; `src/core/test-build.ts` |
| B-270 Files in notes are in backups (#166 slice 4). Format version 2 adds `blobs` (unit, hash, name, size, type), `blob_storage` (`folder`, `zip`, `none`) and `blobs_missing` to the manifest; a version 1 manifest reads as carrying none (`upgradeManifest`). Folder: each hash once in `<account>/blobs/<hash>` (encrypted: named by an HMAC of the hash under a key derived from the passphrase key, content encrypted like every file), plus a readable copy in `current/docs/<space>/attachments/<name>` in plain mode only; restore points keep the index, never the bytes; nothing in `blobs/` is ever deleted. Download: **zip** (store-only, ZIP64, built as a Blob of parts, files at `docs/<space>/attachments/<name>`) and the JSON file, which leaves files out and says so; encrypted mode keeps downloads off | Files are up to 1 GB per space: they cannot sit in the JSON bundle or in the in-memory snapshot, and a zip past 4 GB needs ZIP64 (owner, #166). Copy-once by hash keeps hourly backups cheap; HMAC names keep an encrypted folder from revealing which files you hold. Readable copies sit beside the notes (as `current/` already does for the exports) rather than the design's `attachments/<Space>/` so a zip and `current/` share one layout | `blobs.ts`, `zip.ts`, `FORMAT_VERSION` in `format.ts` |
| B-270b Restore puts each file into the space's store after checking its hash, and merge brings back an index entry that was deleted on this device when the backup holds its bytes; a file the backup lists but cannot supply is counted and reported, not an error | Nothing is collected automatically, so restore is how a deleted file returns; a Yjs merge alone would keep the later delete | `restoreBlobs` |
| B-77 **Back up now** says every outcome on the page, under the buttons: written, nothing changed, failed with its error, no folder. With no usable folder it is a way to get one (the picker for none or a lost folder, the permission prompt for a paused one) and then backs up; a closed picker says so. It is off only when the browser has no folder access, or encrypted mode is on and this device lacks the key, and a line beside it says which. Choosing a folder reports its first backup the same way. Waiting on another tab or a running backup shows "Backing up…" and then the result | Owner saw nothing happen on a newly joined device: the result sat at the foot of the page, a greyed button gave no reason, and the choose-folder backup reported nothing. A locked encrypted device must never fall back to a plain write, so it stays off rather than asking | `backUpNow`, `report`, `backUpNote` in `BackupsView.tsx` |
| B-83 Cover by another device (#83). Each folder backup, each download, and an unchanged check when the last telling is 3 hours old writes one record per space: `cover` map in the space's log document `space/<id>/log`, key = device id, value `{at, kind: folder\|download, encrypted, docs: {<docId>: base64 state vector}}` for the space's shared and private documents the backup holds. A space is **covered** on this device when a record of another device, no older than the stale threshold, holds a state vector with every local client's clock <= the recorded one, for every document of the space held here. A recent record that lacks local changes is **waiting**: no warning until it ages out (same rule as this device's own backup age). `backupHealth` applies cover only when this device's own backup is missing or stale and the device holds data: all spaces covered or waiting gives "Backed up by <device>, <time>"; otherwise it warns about the spaces not covered, naming the device, and says to open it or download. Records of this device, removed or left devices, malformed ones and ones dated more than a day ahead are ignored. Folder-permission and failed-run warnings are never hidden. Settings' Erase device does not use cover. Known limit: a deletion that adds no new item (removing text) leaves the state vector unchanged, so cover can overstate by such edits until the next change | The phone (no folder) should not warn while the laptop backs up the same data every hour, but must warn when it holds a change no backup has. Log documents already sync only between devices that keep the space and are never backed up, so the record cannot reach a device or account without the space and writing it does not change what a backup holds (a map in the space or private document would change the backup's content key on every backup, and a shared document would show device ids to other accounts). One overwritten record per device and space keeps it small. No migration: a new root map in an existing document; older builds ignore it. No permanent dismiss; "Remind me tomorrow" is the only snooze | `src/backup/cover.ts`, `backupHealth` in `service.ts`, `useBackupHealth` in `runtime.ts` |
| B-96 | Replace confirmation names the backup time, the safety copy (folder backup when a folder is set up, plus the data kept on the device) and the undo path "Merge it back"; on a paired device it adds "Only this device changes. Your other devices will send their data back when they connect." | Owner, 2026-10-30 (#96): Replace is hard to do by mistake (safeguards 3 to 5) |
| B-96b | "Merge it back" is offered until dismissed or 45 days after the Replace. Dismissing sets `dismissed_at` on the stored before-replace record and hides the prompt only; the copy is never deleted (data safety). Older records lack the field and count as not dismissed (F39) | Owner, 2026-10-30 (#96) |
| B-107 | **Recently deleted lists every kind** (time entries, notes and tasks, projects, clients, tags, files) in Settings, 45 days (`TRASH_DAYS`, `src/core/trash.ts`), newest first, with Restore and Delete for good. A delete stamps `deleted_at`; projects, clients, tags and files deleted before carry none: "date unknown", listed until deleted for good. Unstamped time entries stay out (a move to another space leaves its original unstamped); notes keep `updated_at` as the date, the later of the two when both exist. A tag merged by a rename is marked `merged` and not listed. No migration or version bump (F39): every field is optional and older builds already skip deleted records | Owner, 2026-10-30 (#107, design note). A version bump would stop older builds syncing the space |
| B-107b | **Delete for good keeps a tombstone:** every field but `deleted` is removed (a note's text with it) and `purged_at` is set; the key stays in its map. `liveRecords` and restore treat a tombstone as gone even if a concurrent restore cleared `deleted`. Backup Merge and moving a note between spaces skip a tombstone (a moved file gets a fresh entry) | A deleted key could be re-created by a stale copy; removed fields cannot come back from an older update (Yjs deletes win over old inserts). Older backups and Version history may still hold a copy; the confirmation says so |
| B-107c | **File bytes stay 45 days after a delete** and go when the file is deleted for good, when the 45 days pass, or at once with the synced account setting `delete_files_now` ("Delete files for good straight away", default off, Recently deleted). The file sweep (`startFileSweep`) runs on every change of a space's index, when the setting changes and every 6 hours; with the setting on it deletes every deleted file for good. A file deleted without a date keeps its bytes. Deleting in the mirror folder no longer drops bytes itself. Half-received pieces of a deleted file are always dropped. Kept bytes count toward the space's file limit. An older build still drops its own copy at once, so restore is offered only where this device holds the bytes | Owner, 2026-10-30 (#107). Undo for files needs the bytes; keeping them is the data-safety default and the setting is the way out |
| B-96c | Picking a backup compares it with now before anything changes: Merge is simulated on a copy of each current document (current state plus the backup's update) and compared with now; Replace is the backup compared with now, a document the backup lacks counting as emptied. Only live records count: deleted ones (Recently deleted included) count as gone, a "deleted for good" marker is never listed. Kinds: time entries, notes and tasks, projects, clients, tags, files in notes, settings (keys of `settings` maps); a changed record (any field, note text included) counts as changed, not as added and removed | Owner, 2026-10-30 (#96): safeguard 1. Simulating the merge is exact where a guess from ids would miss Yjs keeping a later delete; Version history already counts notes and tasks together | `diffBackup` in `src/backup/diff.ts` |
| B-96d | The comparison yields to the browser every 300 records and between documents (`scheduler.yield` where the browser has it, else `setTimeout`), and stops when another backup is picked; no worker | A worker would need its own copy of Yjs and the documents sent to it; chunks keep the page responsive with one code path. Each document's `Y.applyUpdate` still runs in one piece | `yieldToBrowser`, `DiffOptions.chunk` in `diff.ts` |
| B-96e | Replace is offered only once the comparison is ready, and not when it would change nothing; Merge stays the primary button and works at once. The confirmation names what Replace removes ("Removed: 2 time entries") and what it changes back. Backups in the folder are a navigator (list beside the picked backup, like a note's version history); a file, a picked folder or a time opens below the restore buttons. The per-document table moved under "What the backup holds" | Owner, 2026-10-30 (#96): safeguard 2 and the navigator interface | `RestorePanel`, `CompareView` in `BackupsView.tsx` |
| B-96f | **Three layers, one name each:** Recently deleted (trash: records marked deleted inside the data, synced, 45 days), Version history (a log of every change in a separate browser database; each device records its own for now), Backups (full copies plus a change log in files outside the browser, never synced). Every action that replaces state keeps what it replaces; a restore adds and never rolls the log back. Each Settings section says in one line what it covers and where it is stored. A backup restore covers everything; Version history covers time entries, notes and tasks (HI11); Recently deleted one item of any kind | Owner, 2026-10-30 (#96, #97, #107): the owner could not tell backup from history, shared from per-device, or what a restore does to the current state. Built in four PRs; this row replaces the design note | Rename a layer everywhere at once (UI, `docs/user/backups.md`, these rows) |
