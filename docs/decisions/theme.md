# Theme tokens and building blocks: decisions to review

Choices that keep the look swappable: tokens and building blocks.
Each row says what was decided, why, and how to change it.
The step was meant to change nothing on screen; screenshots of every page at 1280 and 375 px, light, dark and both forced themes, match the previous build (`scripts/screens.mjs`).

| Decision | Why | How to change it |
| --- | --- | --- |
| Each colour is written once as `light-dark(light, dark)` in `src/app/theme/tokens.css`; `color-scheme` picks the half, set from `prefers-color-scheme` (no `data-theme`) or from `data-theme` | Light and dark are each defined once, and the system and Settings paths cannot drift apart. `light-dark()` needs Chrome and Edge 123 or later; the probe found 154 and 155 in Chrome and Edge | Edit the pairs in `tokens.css`; the `color-scheme` rules at its top choose the half |
| Existing token names kept (`--bg`, `--surface`, `--surface-2`, `--text`, `--muted`, `--border`, `--accent`, `--ok`, `--warn`, `--info`, `--danger`), plus role tokens (`--running`, `--billable`, `--focus-ring`, `--on-danger`, `--backdrop`, `--qr-light`) | The existing names are already semantic; roles let the running cue or the billable mark be retuned without changing the status colour they borrow | Add a role token in `tokens.css` and use it in the module |
| Type, spacing, radii, shadows, motion and z-layers are tokens; type sizes cover the five most used steps (`--text-xs` to `--text-2xl`); one-off sizes in modules stay literal | Folding every size into the scale would have changed the look; this step had to be invisible | Collapse the remaining literal sizes into the scale when the look is next revised |
| A unit test (`src/app/theme/tokens.test.ts`) fails on any hex, `rgb()`, `hsl()` or similar colour, or basic colour name, in any style sheet except `tokens.css` and `src/style.css`; another fails on a `var(--x)` that nothing defines | Keeps restyling to one file. `src/style.css` is the standalone probe and proof-of-concept page and stays free of app dependencies | Edit `EXEMPT` in the test |
| Building blocks in `src/app/ui/`: `Button`, `IconButton`, `FileButton`, `Pill`, `Field`, `Popover`, `Menu`, `MenuButton`, `toast()` with `ToastHost`, and `icons.tsx` | Modules compose these and keep only layout in their own CSS. `DurationInput` waits for the shared duration parser (T9) in step 2 | `src/app/ui/` and `ui.css` |
| _Superseded by T2:_ the blocks rendered the existing class names and the base look applied to every `<button>` | — | — |
| Every module `<button>` goes through `Button` or `IconButton`, except ones that are not buttons in look (tree rows, tabs, pickers) | Those carry their own module class | Pass an icon from `icons.tsx` as `icon` |
| `icons.tsx` holds our own 16-unit SVG drawings, stroked in the text colour and sized 1em; only the toast's dismiss button uses one so far | One place to swap the set; no icon font and nothing fetched | Redraw or replace the components in `icons.tsx` |
| Popover and Menu are positioned with `position: fixed` and `element.style`, not the Popover API or CSS anchor positioning | Works in every target browser, and setting `element.style` is allowed by the Content-Security-Policy | `Popover.tsx`; `placeBelow` in `popover-logic.ts` |
| Toasts: at most three, newest last, 8 seconds by default, one optional action; the live region is always in the page | Matches the undo toast proposed for U1; a region that exists before the message is announced reliably | `toast-store.ts` |
| The project colour palette moved to `src/app/theme/palette.ts`, used by time and import | It was written twice. A project's colour is data in the document, so retuning the list changes only new projects | Edit `PROJECT_COLORS` |
| The reports field label (`.rp-field`, small and muted above its control) was not moved to `Field` | It labels its control by id, and the reports suite checks that module closely; moving it is not mechanical | Use `<Field layout="stacked">` and give `.field-label` the reports look |
